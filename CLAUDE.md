# CLAUDE.md

Guidance for Claude Code in this repository. [`AGENTS.md`](AGENTS.md) is the router (where things are, conventions); this file adds commands and the sharp edges.

## Commands

| Task | Command |
| --- | --- |
| Put `ezc` on PATH (once) | `direnv allow` |
| Build `ezc` into `cli/bin/` | `mise run cli:build` |
| Test changes to `cli/` (the gate: gofmt, vet, tests) | `mise run cli:test` |
| Same gate with the real-sops and real-git tests required, not skipped | `mise run cli:test:sops` |
| Regenerate the committed manifest JSON Schema | `mise run schema:build` |
| Fail when the committed schema is stale | `mise run schema:check` |
| Build the docs site locally, as GitHub Pages does (Ruby 3) | `cd docs && bundle install && bundle exec jekyll serve` |
| Rewrite the TUI's golden screens (read the diff before committing) | `cd cli && go test ./internal/tui -run Golden -update` |

## Sharp edges

- **Commands reach the outside world only through `System`** (environment, working directory, child processes, streams). Tests drive commands in-process with the fake in `cli_test.go`.
- **Tests never touch the real home**: set `HOME` and `EZC_HOME` to temporary directories through the fake `System`.
- **`cli/schema/v1/manifest.schema.json` is generated** from the Go types in `cli/internal/manifest`; run `mise run schema:build` after changing them. `schemaID` (in `cli/internal/cli/manifestcmd.go`) must change with the file if it moves.
- **`cli/share/env.sh` and `share.ShimVersion` change together.** `ezc repo init` rewrites a repo's shim when its first line differs from the embedded one, unless the shim's version is newer: that one is kept, so a teammate on a newer `ezc` is not downgraded.
- **`ezc env export` never prints to stderr on success and never emits `EZC_ENV` or `APP_ENV`**: the shim discards stderr and mise unwinds variables it owns.
- **The resolver is the only place `~`, `$HOME` and `$NAME` are expanded.**
- **On Unix `ezc run` replaces itself with the command** (`syscall.Exec` in `cli/cmd/ezc/run_unix.go`), so nothing after `RunChild` runs there; `run_other.go` keeps a child process on other systems. The in-process tests use the fake `RunChild`; the real one is tested end to end in `cli/cmd/ezc`.
- **A missing store is fine only at the default location.** A store that is not a folder or cannot be read is an error from `resolve.Load`; an `EZC_STORE` that does not exist is an error from `storePaths` in `cli/internal/cli/scope.go`.
- **`codegen python` refuses a variable named after a Python keyword**; the manifest itself allows it.
- **`doctor` and `storeaudit` print names, counts and paths only, never a value**, and `doctor` never names the encryption tool (its `Differ` and `DifferErr` come from `storeDiffers`, which refuses a file name that cannot be printed before the backend, whose errors name the file, sees it): the policy file names, the key's location and the backend's messages come in through `Options` from `scope.go` and the backend.
- **`doctor`'s `recipients` fix is `recipientsFix`**: `Run ezc user list and check who it names, then ezc store rewrap.` The registry can be the side that is wrong, so the fix never names the re-wrap alone. The repo group's `recipients` item (`repoRecipientsItem`, filled by `repoOptions` in `doctorcmd.go` from `repoDiffers`, so it needs no key) is Broken with `Run ezc repo rewrap.` when the working repo's encrypted files differ from the store's registry, and is left out when the store has no registry, the repo has no encrypted file, or the repo is the store's own folder: the store's item has already said it.
- **`doctor`'s access items come from `storeOptions` in `cli/internal/cli/doctorcmd.go`**: `Request` is `pending` only when a valid pending request (`pendingRequests`) holds this machine's public key, whatever name it has, and `RequestName` is that request's name; with the key only in the environment as text there is no public key and `access` and `recipients`' request lookup are skipped. `Recipients` and `Differ` come from `storeDiffers` (`recipients.Differences` through the backend), which needs no key, and are set before the key is looked up, so the `recipients` item is right when the key is unreadable. The git version is read through `gitstore.Git.Version`; `gitstore.TooOld` judges it against `gitstore.MinVersion`.
- **`doctor` enforces `share.ShimVersion` against the repo's `.ezc/env.sh`.** Change the shim, its first line and `ShimVersion` together, or `ezc doctor` reports a stale shim as healthy or a good one as broken. A shim newer than the binary is a warning there, never a fix to apply.
- **sops runs with its working directory set to the file's folder**, so it finds that folder's `.sops.yaml`; paths given to it are the file's base name.
- **`Backend.Rewrap` refuses a file it cannot read or whose recipients it cannot list before it runs anything**: whether somebody leaves is judged from that list, and a list that could not be read must not count as nobody leaving.
- **`Backend.Rewrap` gives a file a new data key when a recipient leaves it** (`backend/sops/access.go`): `sops updatekeys` alone keeps the data key, which the key that left unwraps from any older commit and which would open every value written afterwards. So the file is put back as it was, rotated (`sops rotate`, while this machine's key still opens it: in `ezc user rotate` the key that leaves is this one) and re-wrapped again. Adding a recipient keeps the data key and the value lines' bytes. The fake backend has no data key; `TestRemoveEndToEnd` and the real-sops tests prove it.
- **A secret reaches sops on stdin only**, never in arguments, the environment or a temporary plaintext file. The backend never passes sops's output through: a failure is the no-key message, the not-installed message (`ErrNoTool`, from every operation that runs sops), the no-matching-rule message (`ErrNoPolicy`) or a fixed "could not read/write this file" message, and "no key" is said only for sops's own no-identity failures. The one exception is `Edit`: `sops edit` owns the terminal, so what it prints there is not filtered.
- **A secret written to a folder with no policy is `ErrNoPolicy` with `writePolicy`'s sentence** (`noPolicy` in `setcmd.go`, also for `edit --secrets` and the backend's no-matching-rule error): `Run ezc store rewrap to write it from recipients.yaml.` in the store, `Run ezc repo rewrap to write it from the store's recipients.` in a repo.
- **`ezc set` declares first**: for a new name it writes the declaration, then the value, and puts the manifest's bytes back if the value write fails. No `set` or `unset` error echoes an argument.
- **`ezc set` writes literally (`$` as `$$`); `--expand` keeps references.** `resolve.Escape` and `resolve.Unescape` are the resolver's own account of that, and `valuefile.SetLiteral` reads the result back through them. A literal leading `~` has no escape and is refused; `--expand` is refused for a secret, resolves the environment after the write and restores the file's bytes when the resolver's `*RefError` names this name in this file.
- **`ezc env import ENV FILE` checks everything, then writes** (`importEnv` in `cli/internal/cli/envimport.go`): `dotenv.Parse` (whose errors name a line, never its text), then every name declared in the scope's manifest, every value through `checkValue` (shared with `ezc set`), the secret boundary and the policy, then `scope.guard` and `guardNewFile`, and only then the writes, which `putBack` undoes on any failure. In the store it commits once, as `import env.ENV`, with the `rotation-due.yaml` entries of the secrets it set cleared. Selector names are a `!` line, never written.
- **`ezc unset` removes only the value**, from the plaintext and encrypted file of the base; `--undeclare` also removes the declaration and is refused while another values file in the scope holds the name. With `-g`, `unsetUsers` runs first (before `scope.guard`, so a refusal writes and commits nothing): `repoUsers` reads the manifest of every repo in `repos.yaml` with a checkout here (a `repos.yaml` that cannot be loaded checks no repo: refused, and with `--force` a `!` line), and a name in `required` (or `optional` with `requiredWhen`) is refused with exit 1 naming the repos, unless `--force`; a plain optional name, a repo with no checkout and a manifest that cannot be read are `!` lines on stdout. A store with no `repos.yaml` has no guard.
- **`Backend.Edit(path, editor)`** passes the editor `ezc edit` validated to sops as `SOPS_EDITOR`. `edit --secrets` needs the file to exist, opens one that fails validation, and checks the result afterwards. `sops edit` exits 200 when nothing was changed; the backend treats that as success.
- **A shim newer than the binary** is a doctor warning ("Upgrade ezc."), and `ezc repo init` keeps it.
- **`enc` is a reserved environment name**; names match `^[A-Za-z0-9][A-Za-z0-9_-]*$`. `codegen python` also refuses a name starting with `_`.
- **The fake backend refuses what sops refuses**: a file holding an unencrypted line cannot be decrypted, set, unset or edited, and the last name of a file is removed without a key. `storeaudit` therefore inspects a file before it decrypts it.
- **The fake backend's file format is not sops's.** Only the real-sops tests (`cli:test:sops`, and the end-to-end tests in `cli/cmd/ezc/sops_test.go`, `store_test.go` and `access_test.go`) prove the real format. They skip without `sops` unless `EZC_REQUIRE_SOPS=1`.
- **The `cli:test:sops` gate requires git as well as sops**: it sets `EZC_REQUIRE_GIT=1`, so every test that runs the real git (`gitstore/gittest`, the store tests in `cli/internal/cli`, `cli/cmd/ezc/store_test.go` and `access_test.go`) fails without it. Under plain `cli:test` and without git, the `gittest` and end-to-end tests skip and the fake `System` in `cli_test.go` answers as a machine that has no git.
- **`cli/cmd/ezc/store_test.go` drives the built binary with real git and real sops** on machines that are a temporary `HOME` and `EZC_HOME`. Each child's environment is built by hand (`newMachine`): nothing is inherited, no key variable is set unless the test is about one, and git sees an empty global config. A second machine gets a copy of the first one's key file before `ezc setup --store`.
- **`cli/cmd/ezc/access_test.go` is the only proof of access against real sops and real git**: almost every other access test uses the fake backend. Its machines come from `newMachine`; `fakeGh` puts a `gh` first on their PATH that records its arguments and stdin in files and does nothing else (the real `gh` may sit beside git on the PATH that follows, so every machine a test makes gets it, a job's included, and a test that expects no call says so with `ghCalls`). `watch` keeps what every command printed and `watch.done` fails when a secret's value or a private key is in any of it or in a commit; `wantShutOut` fails when a key that left a file still unwraps, from any commit, the data key that encrypts the file now, and also when that key unwraps nothing from any commit: it was then never a recipient and the check would pass for nothing.
- **Only `gitstore` builds git command lines**, and `Git.run` drops from the environment the variables that point git at another repo or carry config (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_CONFIG`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT` and the rest of `elsewhere`): git sets them for a hook, and an ezc started from one would act on the wrong repo. Config reaches git only as `-c` arguments. `GIT_TERMINAL_PROMPT=0`, `LC_ALL=C` and `GIT_LITERAL_PATHSPECS=1` are always set.
- **`gitstore.reason` replaces every control character with `?`**, as `ghcli.reason` does: the one line of git's stderr an error carries can be a `remote:` line, which the remote wrote.
- **`gitstore.ShowURL` is the only rule for showing a remote.** A URL keeps its scheme, host and path only, because its user, password, query and fragment can each hold a secret; an scp-style remote and a local path are left as they are. A `gitstore` error carries one line of git's stderr with each URL put through it (`reason`), and `ezc store status`, setup's messages and the `store.remote` that setup saves in `config.toml` use it too. Never write a second rule beside it.
- **`gitstore.Pull` fast-forwards, or rebases the local commits onto the remote's.** A conflicted file for which `keepRemote` is true (an encrypted values file, `resolve.IsEncrypted`) takes the remote's version and is returned as `Replaced`; any other conflict aborts the rebase and leaves the store as it was (a `*ConflictError`, which is `ErrConflict` and lists the files in `Paths`; `ezc store pull` builds its message from the list, never from the error's text). The rebase runs with `-Xno-renames`, so a file renamed here and changed on the remote is a deletion beside a new file, never a rename git follows into the wrong file, and with `--no-autostash` and `GIT_EDITOR=true`.
- **`conflictRefusal` has two sentences.** A conflict that holds `recipients.yaml` or a policy file (`policyFiles`) is two access changes that did not see each other: the files are generated, so the message gives the full-ref `git log` and `git reset --hard refs/remotes/origin/<branch>` and says to make the change again. Any other conflict keeps `Resolve … with git (git pull --rebase)`. `docs/access.md` holds the recovery.
- **`ezc store pull` turns a `Replaced` file into commands, from names only**: `ezc set -g NAME` for a name changed here, `ezc unset -g NAME` for one removed here, with `--env` from the file's name, exit 1. Two machines that each declare a new name conflict in `manifest.yaml` (a plaintext file): that pull stops, and the user resolves it with git. It is a known limit, in the README and `docs/store.md`.
- **`ezc env`, `run`, `list`, `get` and `store audit` call `touchStore` once, before they read the store** (`cli/internal/cli/sync.go`): when the store is a git repo with a remote and the last attempt in `$EZC_HOME/state.json` is 10 minutes old, it fetches with a 3 second timeout, then prints at most one `store:` line on stderr (and a second when the fetch just failed); uncommitted changes are followed by the counts when the store is also ahead, behind or diverged (`alsoStands`). It never fails a command. A store that is not the top of a git repo gets one `git` call, to ask, and nothing else. `ezc env export` never calls it: no git, no line. `state.json` holds `attempted` (the last fetch tried, which the 10 minutes count from) and `fetched` (the last that worked, which the offline line reports); `ezc store status`, `pull` and `push` always fetch, with their own longer timeouts, and set both when they reach the remote.
- **`set`, `unset` and `edit` call `guardStoreWrite` before their first write and commit after their last**, only when the scope is the store (`scope.store`: `-g`, or a working repo whose `.ezc` is the store's). The guard (`scope.guard`) is `touchStore` plus a refusal when the state is not known (`storeSync.Err`) or while the store is behind or diverged, judged from the counts, so uncommitted changes do not hide it, then `guardStoreFiles`: a refusal when a file the write may change already has uncommitted changes (`gitstore.Git.Changed`), because a commit takes a file whole. Give `scope.guard` every file the command may write, and only those: the manifest only when a name is declared or undeclared. `edit` gives none: `edit <file>` is a true name for a hand edit to that file, and a result saved but not valid must be opened again; a successful `edit` commits its file whenever it differs from the last commit. A write to any other repo runs no git at all.
- **An encrypted file of the store is written, pulled and pushed only while it is encrypted for exactly the registry's keys** (`cli/internal/cli/agree.go`; nothing in it needs a key, and a store with no registry is not judged). `scope.guard` ends with `guardRecipients` on the files it was given that exist, `ezc edit -g --secrets` calls it for its file (its `guard` is given none), and `ezc set -g` of a secret calls `guardNewFile`, which compares `Backend.PolicyRecipients` with `registry.Keys()` when the file is not there yet. `ezc store pull` runs `storeDiffers` after every pull, also one that brought nothing, prints a `!` line for each file and exits 1; a `Replaced` file that differs and whose `Base` and `Local` have different recipients (`rewrapped`: the commit lost here was an access change) gets the re-wrap sentence, never `set these again`. `ezc store push` refuses while it is ahead and `storeDiffers` is not empty, and so does `dropRequest`, whose push sends every commit. A machine that has not fetched cannot know its registry is old, so the write is not what stops route A of the final review: the pull and the push are. Never let a push of the store's branch past `storeDiffers`.
- **`commitStore` commits only the files it is given** (base names in the store's `.ezc`), so a hand edit to another file is never swept in, and for `set` and `unset` `guardStoreFiles` has already refused a hand edit to these. The files named in the message are the ones whose bytes differ from before the write (`fileStates`, `changedFiles`), not the ones the command meant to change; none changed means no commit. No commit message holds a value.
- **A failed write leaves no commit because its rollback restores the bytes.** The exceptions: `unset` that removed from one file and then failed commits what it removed, and `edit` that saved an invalid file leaves it uncommitted, and the next successful `ezc edit -g` of it commits it. The commit-failure message carries one line of git's stderr, which a hook the user installed can write: it is the one place here where text ezc did not author reaches output.
- **`behind` in `sync.go` is the one sentence for a store that is behind or has diverged**: ``the store is N commits behind origin. Run `ezc store pull`, then run this again.`` and `the store has diverged from origin (A ahead, B behind). …`. `guardStoreWrite`, `access.guard`, `ezc store push` and `ezc join` all return it; never write a second wording.
- **`sync.go` never names a git subcommand**: it calls `gitstore` methods. In tests the fake `System.Exec` sends `git` to `gittest.Runner` and records it in `fake.gits`, not `fake.execs`.
- **An invalid `config.toml` is an error from `load` and `scopeFor`**, naming the file. `backendFor` and `keySource` use the zero config when it cannot be read; its `key_file` replaces the default key file, and the environment's key still wins.
- **Setup never overwrites a key, a store or a config.** `setup.Key` creates the key file with `O_EXCL` (mode `0600`, its folder `0700`) and only reads one that is there; `NewStore` refuses a store path that has a `.ezc` and, when it fails, removes only what it made; `ezc setup` fills in the fields `config.toml` lacks and keeps the ones it has. A second run prints only `✓` lines and changes no file.
- **Setup adopts a store made by hand and never rewrites what is there** (`setup.Adopt`, run for a store in place and after a clone, before `Publish`). Not a git repo: `Git.Init` and one commit of `.ezc`, `setup: adopt the store`. No `manifest.yaml`: the empty one (`setup: add the manifest` when nothing else is written). Neither a registry nor a policy: both are written as `NewStore` writes them (in the adopt commit, or `setup: add the registry` in a store that was a repo, holding only the files written), but never when the `.ezc` holds an encrypted values file (`resolve.IsEncrypted`, passed in): that store was set up under a policy ezc cannot see, whoever runs setup must not become its one recipient, and setup prints an `!` line in place of `Next:` (`Adopted.Unmanaged`). A registry and no policy: the policy from `registry.Keys()`, `setup: write the encryption policy`. A policy and no registry was written by hand: nothing is written, and setup prints the `!` line in place of `Next:` on every run. `Next:` is printed only when the store has a policy. A store that is a git repo and lacks something is written to only when `Git.Status` can be read: otherwise `Adopt` returns a `*setup.StateError`, which `setupcmd.go` says as `cannotTell` does, and `setup.Adoptable` asks the same question while planning, before the key is made. When `Adopt` fails it removes the files and the `.git` it made.
- **`ezc setup` refuses `EZC_STORE`**: it manages `$EZC_HOME/store`. It also decides what to do about the store before it makes the key, so a different store in place, a missing `gh` or a folder in the way of a clone (`setup.InTheWay`) leaves nothing behind; a clone that fails or is not a store comes after the key is made.
- **Setup registers the key the commands will read with.** The key file is the one the environment names, else the config's `key_file`, else the default path. `keyInEnvironment` in `scope.go` says what the environment supplies to `runSetup`: a key file becomes setup's key file and the config's `key_file` (it must be an absolute path); key text (`EZC_AGE_KEY`, which it reports first, or the backend's own variable) is a `UsageError` before anything is made, in `ezc setup` without `--ci`, `ezc join` and `ezc user rotate`. `runSetup` learns the variable's name only from that helper; `runSetupCI` names `EZC_AGE_KEY` itself, through `botSecret`.
- **`cli/internal/setup` and `setupcmd.go` never name the encryption tool**: the `✓` line is `Backend.Name()`, install text is `Backend.ToolHint` and `Backend.BrewFormula`, a missing tool is `✗ <Name> is not installed.`, the hint and `Then run ezc setup again.` (never the backend's own error text, which sends the user to `ezc doctor`), and the policy file is committed by passing the `.ezc` folder to `Git.Commit`. `gh` and `brew` command lines are built in `setup`; git's only in `gitstore`.
- **A new store's manifest holds `schemaVersion: v1`** with empty `required` and `optional`; without the version `ezc doctor` and `ezc set -g` reject it.
- **Setup writes the store's encryption policy from `recipients.yaml`; `ezc repo rewrap` writes a repo's** (`rewrapRepo` in `repos.go`, through `recipients.Rewrap`, which is `recipients.Apply` without saving a registry: the policy from `registry.Keys()`, each encrypted file re-wrapped and verified, and on a failure the encrypted files and every dot file put back). It is refused before a repo byte is written when the store has no `recipients.yaml`, when `storeDiffers` is not empty, or when the store's policy is not for exactly `registry.Keys()` (`policyIsFor` in `agree.go`, also `rewrapRepo`'s own check; a missing or unreadable policy counts as not), each with `Run ezc store rewrap first.`: a name pushed into the registry is let in by the store's own re-wrap, which asks, before any repo follows it, and in a store with no encrypted file the policy is all there is to compare. It also asks for itself, because whoever can push can rewrite the store's files too: `repoGains` (sorted; it needs no key and asks nothing) are the registry names whose key is in none of a checkout's file recipients and not in its policy; for each target they are computed before any repo is written, printed as `! <names> gain access to <id>'s secrets.` on stderr, and asked about as `Let <names> read <id>'s secrets? [y/N]` through one `asker` for the whole run. Anything but `y`/`yes` is `Not re-wrapped.` for that repo and exit 1 at the end; without a terminal and without `--yes` it is a `UsageError` before any repo is written. A re-wrap where only a key leaves asks nothing. A checkout with neither an encrypted file nor a policy is skipped (`- <id>: no secrets to re-wrap`) unless `create` is set, which only `ezc repo rewrap` without `--all` does: it then gets its first policy, and `repoGains` counts every registry name as gaining, so the question is asked. `rewrapRepos` never creates one, so an access change gives no repo a policy it did not ask for. One already for the registry's keys is not written to, which needs no key. The result stays in the checkout's working tree for its owner to commit: no git runs there. `sayRewrap` prints the success, skipped and `! <id>: <file>/<NAME> could be read by a key that has left. …` lines (`Leaked`, from the names `Backend.Inspect` gives of a file whose recipients held a key the registry does not name; never written to `rotation-due.yaml`, whose keys name the store's files); each caller prints its own failure line, and `repo rewrap`'s is `✗ <id> could not be re-wrapped (<reason>). Nothing was changed there.`, exit 1, or names the files when `recipients.Rewrap` could not put them back (`*repoLeftError`).
- **Every access change goes through `openAccess(sys, true)` and `access.apply`** (`cli/internal/cli/access.go`): never call `recipients.Apply`, `Backend.WritePolicy` or `Backend.Rewrap` from a command. `openAccess` fetches now (30 seconds, whatever `state.json` says) and refuses before a byte is written: state not known (`cannotTell`), a remote that fetch did not reach (`storeSync.Offline` with a remote: nobody else would get the change, and two registries cannot be merged; a store with no remote is not affected), behind or diverged (from `Behind`, so uncommitted changes do not hide it), uncommitted changes to `recipients.yaml`, the policy file, `rotation-due.yaml` or any `*.enc.yaml` directly in `.ezc` (asked of git for the whole `.ezc`, so a file deleted or added by hand counts), no key file in use, no registry, and a key the registry does not name. `openAccess(sys, false)` is for commands that only read: it runs `touchStore`, needs no key and still fails without a registry.
- **`access.run` says who else a change lets in or shuts out before it writes** (I3 of the final review: whoever can push to the store can write a name into `recipients.yaml`, and every access change re-wraps for all of it). `access.effect` compares each file's recipients with `change.next`, leaving out the keys `change.subject` has in the old and the new registry: a name that gains a file is `! <name> gains access to <files>.`, a key the next registry does not name is `! <key>, a key recipients.yaml does not name, loses access to <files>. …` (`announce`; the key through `recipients.Printable`). Every command sets `subject` and `change.confirm`, which `run` calls with the gaining names after the `!` lines and before anything is written, so before `change.extra` delivers a bot's key. A command with a subject uses `alsoLetsIn`: `Let them in too? [y/N]` on stderr, `Nothing was changed.` and exit 1 for anything but `y`/`yes`, and without a terminal a `UsageError` that says to check `ezc user list` unless `--yes` (`alsoYes`) was given. `ezc user approve` passes its own `asker` and its own `--yes`: two readers on one stdin would lose the second answer. `ezc store rewrap` has no subject and its own question, `Let <names> read the store? [y/N]`, with `Not re-wrapped.`. A change where only the subject gains or loses, or where others only lose, never asks. What `confirm` returns reaches the caller inside an `*unchangedError` whose `said` is true (its text is the answer's own, and `errors.As` still finds the `UsageError` or `ExitError`), and an error of `effect` or `strangersDue` is an ordinary `*unchangedError`: `ezc user rotate` removes its new key file on both. `strangersDue` wraps `change.due` so that every name in a file a stranger's key leaves gets a rotation-due entry under that key (`Due.Add` keeps an entry that is there): it is what records a secret written under a stale policy, whose commit the re-wrap then pushes. `effect` also reads the policy's keys (`Backend.PolicyRecipients`): a name of `change.next` that no file showed and the policy lacks gains `secrets set from now on`, which is the only comparison a store with no encrypted file has. `run` reads the commit it made (`Git.Head`) right after `Git.Commit` and gives that to `uncommit`, so a commit another command makes while the push runs is never taken back: `Git.Uncommit` then refuses and the result is an `*unpushedError`.
- **`ezc store pull` prints `! recipients.yaml changed on the remote: + a - b ~ c (new key). …`** when the registry it loads after the pull differs in names or keys from the one it loaded before (`registryChange`), on stderr, and that alone does not change the exit status. The names passed `recipients.Load`'s rule. A registry that cannot be loaded afterwards is `storeDiffers`' error line.
- **`access.apply` runs, in order**: `recipients.Apply`, `change.due` on the loaded `rotation-due.yaml` (skipped when nil: the file is then not read; `strangersDue` makes it non-nil when a key the registry does not name leaves a file), `change.extra`, the removal of `change.remove`, one commit of the files whose bytes changed (`changedFiles`), a push when the store has a remote. `access.run` is the same and says whether a file changed; no change means no commit, no push and no line, which `ezc store rewrap` reports itself. When `run` changed a file and its error is nil or an `*unpushedError` (the commit exists here), it then re-wraps every repo of `repos.yaml` with a checkout here (`rewrapRepos`, decision 8 of part 5) with `a.b`, the backend `openAccess` built, so `ezc user rotate` re-wraps its repos with the old key; no command calls it itself. Its lines follow the store's on `a.sys.Stdout`. A repo that fails, has no checkout here, or whose re-wrap would let in a name that is neither the change's subject nor one its `confirm` was answered yes about (`letIn`) is left as it was with a `!` line naming `ezc repo rewrap <id>`, and never changes the exit status. A routine `user rotate` or `bot rotate` sets `change.retired` to the old key, whose leaving lists no repo secret; with `--compromised` each is listed (`sayRewrap`).
- **A failure up to and including the commit restores** `recipients.yaml`, `rotation-due.yaml`, the policy file, the encrypted files and the `change.remove` files: `Git.Restore` on the ones that changed, then their bytes from before, which is all a plain folder has. The error then ends `Nothing was changed.` (`*unchangedError`, which unwraps), or says the store could not be put back: when a file's bytes still differ, and when `Git.Restore` failed and git still lists one of the files (a failed commit leaves them staged). A commit git does not make because it ignores the files is such a failure too. What `change.extra` did outside the store is not undone.
- **A push the remote refuses because it moved takes the commit back; any other push failure leaves it.** `Git.Push` wraps `gitstore.ErrRemoteMoved` when origin's branch, asked of origin after the failure, is not an ancestor of `HEAD`. `access.run` then calls `Git.Uncommit(dir, parent, made)` (`update-ref` of the branch's full name with the old value, so the index and the work tree are not touched and a hand edit elsewhere survives) and `access.restore`, and returns an `*unchangedError` whose `then` is `pullFirst`: `The store's remote changed while this ran. Nothing was changed. Run ezc store pull, then run this again.` No `✓` line is printed for a commit that was taken back. Any other failure is `Committed, but the push failed (<reason>). Run ezc store push.` (`*unpushedError`, which unwraps; a caller with work to do only after a push tests for it), exit 1, after the `✓ <message>` line, and so is a commit that could not be taken back. `change.pushed` (only `ezc user rotate` sets it) takes the commit back after any push failure: `The push failed (<reason>). Nothing was changed.` `Git.Push` sends every commit the store is ahead by and has no timeout. A store with no remote gets the commit and no push; a store that is not a git repo gets neither. `dropRequest` (`ezc user deny`) does not take its commit back.
- **`apply` prints to `a.sys.Stdout`** (`✓ <message>`, `✓ pushed to <ShowURL(remote)>`); a command whose stdout carries something else points the `access`'s copy of `System` elsewhere first.
- **What `ezc user list` prints from the store is untrusted**: a name passed `recipients.Load`'s rule, and the owner, dates, `addedBy` and unregistered keys go through `recipients.Printable`. `openAccess` refuses a store with an encrypted file whose name `Printable` would change, so no later message, the backend's included, can carry one raw. `ezc user add` never echoes its key, and its name only once `recipients.ValidName` accepts it (checked before `openAccess`, a `UsageError`): either may be a private key pasted by mistake.
- **`ezc user remove` refuses before it writes**, in this order: an invalid name (a `UsageError` before `openAccess`, never echoed), not a recipient, a bot, `recipients.ErrLast`, `*OwnsError` (decision 7), this machine's own entry unless `access.otherWayIn` finds another user or machine of the same person. It prints the secrets list after `apply`'s lines, and also after an `*unpushedError`, because the commit exists.
- **`dueFor` takes names from `Backend.Inspect`, so it needs no key**, and `recipients.Due.Add` keeps the entry a name already has: the first removal's date stays. `ezc set -g` of a secret and `ezc unset -g` of one clear their entry (`scope.pendingRotation`, `clearRotation`) and give `scope.guard` and the commit `rotation-due.yaml` only when the entry exists; a plaintext value never has one. `ezc unset -g` clears an entry also when it removed nothing, because the secret left its file in an editor or with the file: it then prints that the name is not set and no longer needs a new value, and exits 0. `ezc edit -g --secrets` never clears one. `sayDue` prints each secret as `dueLine` gives it: the `ezc set -g NAME [--env E]` that writes it (`envFlag`, shared with `replacedNote`), or `<file>/<NAME>` through `Printable` when the file or the name could not be that command's argument. If clearing the entry fails after `set` wrote the value, `putBack` restores every watched file from `fileStates` and nothing is committed; `unset` that removed the value and then cannot clear the entry commits the removal (the existing `unset` rule) and leaves a stale entry. `storeSync.Due` counts the entries for `ezc store status`; `--due` reads the file and does not fetch.
- **A bot's key is delivered before the commit** (decision 4, `giveBotKey` in `cli/internal/cli/botcmd.go`): `change.extra` runs `Backend.CanDecrypt` on every encrypted file with the new private key, then `ghcli.SecretSet(repo, botSecret, private)` for each repo. Either failing restores the store through `apply`, so no commit ever registers a key no repo holds. `gh` missing is refused before `openAccess` for `bot add` and before `NewKey` for `bot rotate`. A secret that was set is not taken back, so `giveBotKey` keeps `given`, the repos that took the key, and any failure that is not an `*unpushedError` with `given` non-empty (a later repo refusing, the commit failing after all of them, or the remote moving under the push) names those repos as holding a key the store does not name, says `The store was not changed.` in place of `Nothing was changed.`, and names the command to run again, after `ezc store pull` when the `*unchangedError` has a `then`.
- **A bot's private key is a `[]byte` that goes to three places only**: `Backend.CanDecrypt` (the text `NewKey` returned, which is a key file's and may open with comment lines), and its one secret line, `backend.SecretLine`, to gh's stdin and to stdout under `--print-private`. `NewKey` keeps returning the key-file text because `setup.Key` writes it to a file. Never a string that outlives the call, an error (the backend's `CanDecrypt` error is dropped for that reason, and `ghcli` drops a stderr that repeats stdin), an argument, the environment or a file. With `--print-private` stdout is that one line and nothing else: `giveBotKey` points the `access`'s `Stdout` at stderr and returns `out`, the writer every other line of the command must use. That write comes after the commit and is checked: a failure is exit 1 saying the bot is registered and to run `ezc bot rotate <name> --print-private`. `ghcli` drops a stderr that holds any line of stdin, anywhere in it.
- **`ezc bot add` refuses a `--repo` that another bot's entry names**, after `openAccess` and before the key is made: a repo holds one `EZC_AGE_KEY`, so a second bot would replace the first one's key and `bot remove` of either would delete what the other reads with. It also refuses a `--repo` that is not in `repos.yaml` (`<repo> is not in repos.yaml. Run ezc repo add <repo> first.`), read after `openAccess`'s fetch; `bot rotate` and `bot remove` act on an entry's repos as they are.
- **A bot entry's `repos` are untrusted**: whoever can push to the store wrote them, and they become `gh` arguments. `bot add` takes only `setup.IsSlug` repos (a `UsageError` that states the rule and never echoes the argument, as for the name); `bot rotate` refuses an entry holding one that is not a slug, shown through `recipients.Printable`; `deleteBotSecrets` skips it with a `!` line.
- **`ezc bot remove` deletes the repos' secrets only after the registry change is made**: after `nil` or an `*unpushedError` (the key is out of the registry here), never after an `*unchangedError`. A failed delete, or `gh` missing, is a `!` line and never changes the exit status. `EZC_STORE_TOKEN` is the user's and is never touched. `bot rotate` writes rotation-due entries only with `--compromised` (decision 6), as `<name> (old key)`; `sayDue` in `usercmd.go` prints the list for `user remove`, `bot remove` and `bot rotate`.
- **"Cannot tell" refuses a write and never fails a read.** `storeSync.Err` is set when the store is a git repo and `Git.Status` fails (`gitstore.ErrNoBranch`: a detached `HEAD`, as while a rebase is open) or git is missing and the store has a `.git` entry (`Git.IsRepo` then returns true with `ErrNotInstalled`). With it set `Status` is the zero value and means nothing: `indicate` prints one red `store: cannot tell how the store stands in <dir> (<reason>)` line, `guardStoreWrite` refuses before any byte is written, doctor's `sync` item is Broken with the guard's sentence (`cannotTell`), and `ezc store status`, `pull` and `push` exit 1 (`storeUnread`). `env`, `run`, `list` and `get` print the line and carry on. A plain folder is `Git: false` with or without git, and stays silent.
- **A request's name is shown only when `recipients.ValidName` accepts it** (`requestNames` in `sync.go`): whoever can push to the store names the `ezc/join-*` branches and the files in `.ezc/requests/`, and the name goes to the terminal. A name that fails is left out of every output, not listed as invalid.
- **Pending requests are the union of `origin/ezc/join-*` (as of the last fetch) and the working tree's `.ezc/requests/*.yaml`.** `requests` gives `syncStore` the names for the `store:` line, `ezc store status` and doctor with one extra git call (`Git.RemoteBranches`), made only when the store has a remote, and its failure is no names: it never fails a command. `requestNames` counts the branches and files whose names fail `ValidName` (`hidden`), and `ezc user requests` says how many on stderr: nothing else shows them and no command takes such a name. `pendingRequests` also reads each request and is called only by `ezc user requests`, `approve` and `deny`, with the same `remote` flag, so a store that is no git repo or has no remote is never asked about branches. The `store:` line and `ezc store status` name five and count the rest (`someNames`).
- **`ezc user approve` never merges, checks out or reads anything of a request branch but `.ezc/requests/<name>.yaml`** (decision 1): a branch that also changes `recipients.yaml` or a values file changes nothing. The entry it adds is built from the parsed request and goes through `Registry.With` and `access.apply`, like `user add`. Never replace this with a merge or a cherry-pick.
- **`gitstore` names every ref in full and fetches no tags, because a tag can shadow a branch's short name. That makes reads tag-proof, not pushes.** A tag on the remote whose own name is `refs/heads/<branch>` makes the full name match two refs there, and git refuses the push or the delete: `Git.push` then returns a `*gitstore.TagError`, whose fixed sentence names the tag and says to delete it. A ref of the remote is asked for by its exact full name (`remoteRef`): `ls-remote` matches the end of a name, so `a/refs/heads/x` would answer for `refs/heads/x`. Git resolves `origin/main` or `ezc/join-sam` among `refs/tags/` before the branches, and anybody who can push can make such a tag. So a remote-tracking branch is `refs/remotes/origin/<branch>` (`tracking`), a branch to push or delete is `refs/heads/<branch>` on both sides of the refspec (`head`), every fetch and clone runs with `--no-tags`, the current branch is read with `symbolic-ref` without `--short`, and `PushBranch` goes back with `git switch`, which takes a branch only. Never pass a short ref name to git, and never take `ls-remote`'s first line; `TestTagsNeverStandInForABranch` holds a store that already has the hostile tags.
- **A request is read at one commit and never again.** `pendingRequests` resolves the branch once (`Git.RemoteCommit`), reads the file and the author at that commit (`ShowAt`, `LastAuthorAt`) and keeps it in `pending.Commit`. `approve` shows that `pending`, asks, and registers from the same value: nothing fetches or reads between the question and `apply`. The branch is then deleted with `Git.DeleteRemoteBranch(dir, branch, commit, …)`, which refuses (`gitstore.ErrBranchMoved`) when the remote's branch is elsewhere and pushes with `--force-with-lease=refs/heads/<branch>:<commit>`; a moved branch is a `!` line in `approve` (`requestArrived`) and an error in `deny`.
- **`ezc user approve` asks `Approve <name>? [y/N]` on a terminal and needs `--yes` or `--key` without one**: `--key KEY` answers only that question and only when the request holds exactly KEY (`The request of <name> holds another key than the one given. Nothing was changed.` otherwise); it never reaches `alsoLetsIn`, which only `--yes` answers. The TUI approves with `--key`. Neither flag without a terminal is a `UsageError`, raised after the refusals and before anything is printed. Anything but `y`/`yes` prints `Not approved.`, exits 1 and changes nothing. The prompt is on stderr (`asker`) and holds only the validated name. The path that only cleans up after an earlier approval grants nothing and never asks.
- **Everything in a request is untrusted**: the name, kind and owner pass `recipients.ParseRequest` (the name inside must be the file's), the key `Backend.ValidRecipient`, and the host, date and Git author are printed only through `recipients.Printable` (`showRequest` in `usercmd.go`). A request that fails is kept with `pending.Err`, whose text is one of the fixed sentences of `ParseRequest` or `pendingRequests`, listed as not valid and never approved; `Req` is then the zero value. A working-tree request that is not a plain file is not read. A name under which the branch and the working tree hold different requests is not valid.
- **`approve` and `deny` use the request as the remote holds it at the fetch `openAccess(sys, true)` just made**, which reached the remote: `openAccess` refuses every access change when it did not. `approve` prints the whole public key (`showRequest`) after every refusal and before `apply`, so the key printed is the key added. `ezc user requests` fetches too, whatever `state.json` says, and when it cannot it lists what was known with a `!` line on stderr.
- **The request branch is deleted only after `apply` returned nil.** After an `*unpushedError` it is left, with a `!` line. A second `ezc user approve <name>` that finds the name registered with the request's key adds nothing and only clears what is left (the branch, and a merged request file through `dropRequest`); it refuses while the store is ahead, so the branch never goes before the registry that names its key is on the remote. A branch that cannot be deleted is a `!` line and exit 0.
- **`ezc user deny` does not go through `access.apply`** (`dropRequest`): it changes nobody's access, so it must not rewrite the registry, the policy or an encrypted file. It commits the removal of the file alone as `deny <name>` and pushes, then deletes the branch, so a commit that fails leaves both and `Nothing was changed.` is true; it reuses `access.restore`, `*unchangedError` and `*unpushedError`.
- **`ezc user rotate` runs the re-wrap with the old key and moves `key_file` only after the proof** (`cli/internal/cli/usercmd.go`): the new file comes from `setup.Key` (`O_EXCL`, `0600`) at `freshKeyFile`'s path, `change.extra` runs `CanDecrypt` with the text read back from that new file and then saves `key_file`, and an `*unchangedError` removes the new file and puts `config.toml`'s bytes back. Its change sets `pushed`, so a push that fails for any reason is an `*unchangedError` too: a rotation that stayed here would leave this machine reading with a key the remote's files are not for (I1 of the final review). An `*unpushedError` reaches it only when the commit could not be taken back, and any other error means the store could not be put back: both keep both key files and name them. `delete it when you are sure` is printed only after `apply` returned nil, and when `rewrapRepos` left a repo with a checkout here as it was (`access.left`) the line says to keep the old key and re-wrap with it (`keyFileVariable`, from `scope.go`, set to the old file): those repos are still encrypted for it, and `ezc repo rewrap` reads with the new one. A key file the environment names is refused; the old file is never touched. Decision 6: rotation-due entries only with `--compromised`.
- **`EZC_AGE_KEY` is the one private key ezc puts in a child's environment.** `backendFor` passes its text as `sops.Options.Key`, and the backend gives it to sops as `SOPS_AGE_KEY` with no key-file variable and without what the environment said about a key: the text was already in the environment ezc was given. It is one secret line (`backend.SecretLine`, what `ezc bot add` delivers) or a whole key file's text. It wins over everything else: `keySource` reports it first, `keyInEnvironment` returns it as key text, and `keyFileInUse` is false with it, which is what makes every access command refuse in CI (decision 8, in `openAccess`). The fake backend has no key in the environment, so that refusal is tested with `System.Backend == nil`.
- **A token reaches git by name only, and only for github.com.** `tokenVar` in `sync.go` is the one place that decides the variable: `EZC_STORE_TOKEN` when it is set; else `GH_TOKEN`, only while `EZC_AGE_KEY` is also set (a CI run); else none, so a developer with `GH_TOKEN` exported keeps git's own credentials. `storeGit` and `runSetupCI`'s missing-token check both ask it. `Git.remote` then puts two `-c credential.https://github.com.helper=` settings before every clone, fetch and push: the first drops the inherited helpers for that host, the second is a shell function that echoes `password=$<VARIABLE>`. Both are scoped (`tokenHost`), so no other host is offered the token and its helpers stay; `TestTokenIsOfferedToGitHubOnly` proves it with real `git credential fill`. The value is never in an argument, a URL or `.git/config`. `--ci` therefore works with github.com only.
- **`ezc setup --ci --store` is `runSetupCI`**, a separate path from `runSetup`: `--store` is `owner/repo` or an absolute local path (an invalid one is never echoed, since a URL can hold a password), `--new-local`, `--new-github` and `--name` are a `UsageError`, and a missing `EZC_AGE_KEY`, one that `Backend.ValidKey` refuses, or a missing token is exit 1 before anything is made. After the store is in place `Backend.CanDecrypt` on its first encrypted file, when it has one, must accept the key, else `✗ The key in EZC_AGE_KEY cannot read this store.` and exit 1 with the clone kept and no config written; `✓ the key:` is printed only after that. `setup.CloneShallowStore` clones with git, never `gh` (a slug becomes `https://github.com/<slug>.git`), one commit deep. It writes `backend` and `store.remote` and never `user` or `key_file`, makes no key file, never adopts or writes to the store, never prompts or installs, and prints no `Next:`. A store in place is kept when `sameRemote` says it is the one asked for: the same URL or path, or, for an `owner/repo`, exactly that repo on github.com (`onGitHub`), never another host or a longer path that ends the same way.
- **`ezc setup --store` checks out the remote's default branch.** A bare repo whose `HEAD` names a branch nobody pushed clones as an empty folder, and setup then says it is not an ezc store; the end-to-end tests create their bare repo with the store's branch name for that reason.
- **`ezc join` writes nothing to the store's own branch.** It clones (or keeps a store whose remote is the one asked for, by `sameRemote`, and that its own fetch shows is neither behind nor ahead, since the request's branch is cut from the store's last commit), then makes the key and fills the config's empty fields as setup does, with setup's helpers. The request file is written to `.ezc/requests/<name>.yaml` only to be handed to `gitstore.PushBranch`, which takes it out of the work tree again; `joincmd.go` passes that one path and nothing else, because `PushBranch` restores every path it is given. Nothing of the registry, the policy or a values file is touched.
- **`ezc join` decides "already asked" from the key, not from the bytes.** A request on `origin/ezc/join-<name>` (as of the clone or the fetch join just made) or in the store's `.ezc/requests/` that parses and holds this machine's public key is the same request, whatever its date or host: nothing is pushed and no pull request is opened. Any other content under that name, an entry of that name in `recipients.yaml` with another key, and `ErrBranchTaken` from the push (the branch appeared since the fetch) are all the one sentence `The store already has a recipient named <name>. Pick another name with --name.`
- **`ezc join` saves `config.toml`'s `user` last** (`settle` in `joincmd.go`): after the request was pushed, or found waiting or in the store with this key, and for a key that is already a recipient the registry's name for it (a machine's owner), never `--name`. A taken name, a push that failed or any earlier error leaves `user` unset; a `user` that is there is never replaced, and a `!` line says when it differs. `backend`, `key_file` and `store.remote` are filled right after the key, as setup fills them.
- **`ezc join` never echoes `--name`, `--kind`, `--owner` or its argument when they fail validation**: the message states the rule. A path that is not a folder is refused before git runs, so git never quotes it. The public key may be printed; `ezc join --print` puts exactly one line on stdout (`ezc user add …`) and the notice about a new key on stderr.
- **The pull request is a courtesy.** It is opened only when `gh` is on PATH and the store is on GitHub (the argument was `owner/repo`, or `onGitHub` says so of the remote); its failure is a `!` line and exit 0. `ghcli` is the only place besides `setup` that builds a `gh` command line; `GH.SecretSet` puts the value on stdin and nowhere else, and a `ghcli` error is one line of gh's stderr with each URL through `gitstore.ShowURL` and control characters replaced, or the fixed `gh: it failed` when that stderr repeats what stdin held.
- **`System.Hostname`** is the request's `host`. The fake in `cli_test.go` answers `test-host` unless `fake.hostname` is set.
- **The working repo is the folder holding the nearest `.ezc/`** (`workingRepo` in `cli/internal/cli/repos.go`), and the store is never a repo of its own `repos.yaml`: a working repo whose `.ezc` is the store's (`sameDir`) is refused. Its ID is the `owner/repo` of its `origin` when that is on github.com (`githubSlug`, which `sameRemote` uses too: one parser, through `gitstore.ShowURL`), else `--name`, else the folder's base name; a non-GitHub `origin` gets a plain name. Reading `origin` (`Git.Remote`, any error meaning none) is the only git call made in a repo that is not the store. An ID or `--name` that fails `registry.ValidID` is a `UsageError` that states the rule (`repoIDRule`) and never echoes it.
- **A repo's checkout here is `config.toml`'s `[checkouts]` path when that folder holds `.ezc/`, else the working repo when the ID is its own** (`checkoutOf`, which never writes the config). `ezc repo add` records a checkout only for the working repo: with another ID it registers that ID and records nothing. A `[checkouts]` entry for the ID whose folder still holds `.ezc/` is kept with a `!` line; one whose folder does not is replaced: it is the one config field ezc overwrites.
- **`ezc repo add` and `ezc repo remove` commit and never push**, like a value change: `guardStoreWrite`, then `guardStoreFiles(…, "repos.yaml")`, then one `commitStore` of `repos.yaml` alone as `repo add <id>` / `repo remove <id>`. A repo that is already registered is `✓ <id> is registered` and no commit. `repo remove` is refused while a bot's entry in `recipients.yaml` names the repo (naming the bot and `ezc bot remove`), and also drops this machine's `[checkouts]` entry. `ezc repo list` prints `added` and `addedBy` through `recipients.Printable`, and `registry.Save` writes every value that is not a plain word as a JSON string, so an `addedBy` with a newline that `Load` accepted is saved as valid YAML; a `repos.yaml` that fails `registry.Load` fails it as a whole.
- **`ezc repo check` and `ezc repo uses` read only, and `repoTargets` (`repocmd.go`) is the one rule for which repos a command acts on**: no argument or `.` (`workingID`, so that ENV can follow) is the working repo (registered or not), an ID is that registered repo (`<id> is not in repos.yaml.` otherwise), `--all` is every registered repo and then the only argument is ENV, which `repo check` validates with `checkEnvName`. A checkout is `checkoutOf`, so a recorded folder that is gone is no checkout: it is listed, never a failure. A check is `ezc env`'s (`loadManifest`, `load`, `check.Run`) in the checkout, with its stderr notes and report indented on stdout under `<id> (<checkout>)`, plus `repoDiffers` (`recipients.Differences` of the checkout's encrypted files against the store's registry, when it has one); exit 1 when either fails. `touchStore` runs once, before the registry is read. Output holds names, counts and paths only. `ezc repo rewrap` takes the same arguments, except ENV.
- **`docs/superpowers/` is history.** Specs and plans describe what was intended at the time; don't edit them to match the code.
- **`internal/tui` imports no ezc package and never `System`**: it sees ezc through the interfaces in `tui/deps.go`, which `cli/internal/cli/tui.go` implements. `go list -deps ./internal/tui | grep easy-config` must print only the package itself.
- **Every change the TUI makes is an ezc command line run by `tuiCommands.Run`**, shown on the confirm screen first: `cli.Run` in-process with stdout and stderr in one buffer, stdin the given text, every `…IsTerminal` false and `ReadSecret` failing, so the command asks nothing and refuses what it would have asked about. The TUI never passes `--yes`: it approves with `ezc user approve NAME --key KEY`, the key its confirm screen showed. `Run` also wraps `Exec` so that a program wired to the terminal (`proc.Command.Interactive`: brew, an editor) is refused, with a `! <name> needs the terminal` line, because the TUI owns it; so the wizard offers no brew install. A secret's value goes on stdin, never in the line. Never give the TUI a write path of its own.
- **Untrusted text is cleaned where it enters the TUI's model**: every string of a load result, an outcome line, the header and the confirm screen's notes goes through `tui.clean`, which replaces each control character with `?`. `fit` does not clean, because the rows it fits carry the TUI's own colours; a string that reaches a row without passing a `loaded` or `confirm` is a bug.
- **A revealed secret is dropped, not hidden**: `valuesPane.forget` zeroes it and moves `rseq` on, so a reveal that arrives after a move is dropped, and every move (selection, view, scope, environment, a load, a confirm screen, a run) calls it. Every pane's load carries a `seq`; a result whose `seq` is not the pane's latest is dropped. Golden files never hold a secret value.
- **`ezc tui` opens the wizard when the default store has no `.ezc`**, and `ezc setup` opens it when there is no store, no flag at all was given, stdin and stdout are terminals and `System.RunTUI` is set; the fake `System` sets `RunTUI` to record the model and `StdoutIsTerminal` false, so setup tests keep the line prompts. The wizard runs setup in-process without a terminal, so it never opens itself again.
- **`ezc migrate` writes nothing until the proof passes** (`cli/internal/migrate`): the new `.ezc` is built in `os.MkdirTemp("", "ezc-migrate-")`, the environment before is the old tool's own `codegen shell` output (run through `System.Exec`, stderr dropped, `APP_ENV` never passed, `FS_CONFIG_HOME` set for a store), the environment after is `resolve.Load` over the staging folder (a resolver error names `.ezc`, not the temporary folder), and only identical names and values let `place` copy it into `<dir>/.ezc` (`os.Mkdir`, so an `.ezc` that appeared is not overwritten). A store keeps `.fs-config/`; a repo's is removed after `.ezc/` and its mise files (`miseFiles`) are written, and a failure before that puts back the mise files already written and removes `.ezc/`. The old tool runs with `oldToolTimeout`. No git runs. The proof's output and every error hold names, counts and paths only. `migrate` learns the CI key variable from `keyTextVariable` in `scope.go` and copies the policy file without naming it.
- **The name rule has two exemptions**: `cli/internal/migrate/` and `cli/share/skills/ezc-migrate/` may name the tool ezc replaces; nothing else under `cli/` may, and `Four Signals` and `ipm` are banned in those two as well. Tests elsewhere use `migrate.OldTool` and `migrate.OldDir`.
- **`ezc setup` installs the skills in `cli/share/skills/`** (embedded as `share.Skills`) through `setup.InstallSkills`, after the config and before `Next:`, under `$CLAUDE_CONFIG_DIR` or `~/.claude`: missing is installed, different is replaced, identical is kept (`✓`), and a failure is a `!` line that never fails setup. `--ci` installs none. A second setup prints `✓ the skill …` lines, so the setup tests' expected outputs carry `setupSkillsInstalled` or `setupSkillsKept`.
