# AGENTS.md

Router for agents working in this repo: the source code of `ezc` ("easy config"), a Go CLI that composes a repo's environment from a global store of secrets and variables and the repo's own `.ezc/`, validates it against a manifest, and exports it or runs a command with it. Read the linked file for detail; this page is only where things are.

The design and its parts are in [the ezc design](docs/superpowers/specs/2026-10-10-ezc-design.md); parts 1 (core), 2 (secrets) and 3 (`ezc setup`, the store as a git repo, and its sync) are built. Part 4 (access) is built too: `ezc join`, `ezc user list`, `add`, `remove`, `requests`, `approve`, `deny` and `rotate`, `ezc bot add`, `remove` and `rotate`, the rotation-due list, `ezc store rewrap` and `ezc setup --ci`. Part 5 (the registry of repos) is built: `repos.yaml`, `ezc repo add`, `remove`, `list`, `check`, `uses` and `rewrap`, the `ezc unset -g` guard, and the re-wrap of the repos checked out here after every access change. Part 6 (the TUI) is built: `ezc tui` and its four views (values, access, repos, doctor), and the setup wizard that `ezc tui` and `ezc setup` on a terminal open.

## Where things are

| Path | What it is |
| --- | --- |
| `cli/` | `ezc`, the Go CLI. Every command is in `cli/internal/cli`; `cli/cmd/ezc` only wires the process into `cli.Run`. |
| `cli/internal/backend` | The interface to an encryption tool (`Name`, `Check`, `HasPolicy`, `Inspect`, `Decrypt`, `Set`, `Unset`, `Edit`, for setup `NewKey`, `PublicKey`, `WritePolicy`, `ToolHint`, `BrewFormula`, and for access `Recipients`, `PolicyRecipients`, `Rewrap`, `CanDecrypt`, `ValidKey`, `ValidRecipient`), a fake for tests that needs no tool (it keeps files in its own format on disk), and `backendtest`, the contract every backend passes. |
| `cli/internal/backend/sops` | The one place that knows `sops` exists: runs the program, picks the age key (a key file, or the key's text from `Options.Key`), makes a new key and reads a key file's public half, writes a folder's policy from a list of public keys, reads a file's recipients, re-wraps it (with a new data key when a recipient leaves), and turns its failures into fixed messages. |
| `cli/internal/paths` | Where ezc keeps things on a machine: `EZC_HOME`, and in it `config.toml`, `state.json` and the store. |
| `cli/internal/config` | Loads and saves the machine's `config.toml`: `user`, `backend`, `key_file` and the store's `remote`. |
| `cli/internal/recipients` | The registry of who can decrypt a store, its `.ezc/recipients.yaml`: load, save, the changes to it (`With`, `Without`, `WithKey`), the list of keys the policy is written from, and the rule for a recipient's name (`^[a-z0-9][a-z0-9-]*$`). Also a join request (`Request`, `ParseRequest`, `.ezc/requests/<name>.yaml`), the secrets that need a new value (`Due`, `.ezc/rotation-due.yaml`), the change sequence every access change runs (`Apply`: registry, policy, re-wrap, check, and everything put back when a step fails), `Differences` between the files and the registry, and `Printable`, which makes text from a remote safe for a terminal. |
| `cli/internal/registry` | The store's list of the repos that use it, its `.ezc/repos.yaml`: load (strict, an invalid entry fails the whole file), save, `With` and `Without`, the rule for a repo's ID (`owner/repo` or a plain name, `ValidID`), and `Uses`, how a manifest declares a name. |
| `cli/internal/proc` | The description of a child process (`Command`) and the runner type the backend is given, so tests can fake it. |
| `cli/internal/valuefile` | Edits plaintext values files and manifests in place (`ezc set` and `unset`): comments kept, written through a temp file and rename, read back before it replaces the old. |
| `cli/internal/storeaudit` | Audits a store's values files against its manifest (`ezc store audit`): undeclared, missing, secret-boundary, leak, placeholder and shape findings, never a value. |
| `cli/internal/gitstore` | The one place that builds `git` command lines: a store's status against its remote, fetch, commit, push (`ErrRemoteMoved` when the remote refused it for having moved), `Uncommit`, which takes one commit back without touching the work tree, and `Pull`, which rebases local commits and keeps the remote's version of a conflicted encrypted file. `gittest` runs the real git for tests, cut off from the user's config. |
| `cli/internal/cli/sync.go` | What a command learns about the store before it uses it: the fetch every 10 minutes recorded in `$EZC_HOME/state.json`, the `store:` line on stderr, the pending access requests (`requests`, `pendingRequests`), the refusal to write while behind or while the store's state cannot be read (`behind`, the one sentence for it), and the commit after a write. |
| `cli/internal/cli/storecmd.go` | `ezc store status`, `pull`, `push`, `rewrap` and `audit`. Pull turns the files `gitstore` replaced into the `ezc set -g` lines to run again, from `valuefile.ChangedNames`: names only; it also says when the registry's names or keys changed and names every file that is not encrypted for it. Push refuses while such a file exists, and rewrap asks before it lets a name in. |
| `cli/internal/cli/agree.go` | The rule that an encrypted file of the store is written, pulled and pushed only while it is encrypted for exactly the registry's keys: `storeDiffers`, `scope.guardRecipients` and `guardNewFile` for a write, and `rewrapped`, which tells a re-wrap from a changed value in a file a pull replaced. Needs no key. |
| `cli/internal/cli/access.go` | The one path every change to who can decrypt the store takes: `openAccess` (the store, its registry, this machine's key, and every refusal before a write, an unreachable remote among them) and `access.apply` (who else the change lets in or shuts out, the sequence, one commit, the push, the restore when a step fails, and the commit taken back when the remote moved). |
| `cli/internal/cli/usercmd.go` | `ezc user list`, `add` and `remove` (and `dueFor`, what a removal leaves to rotate), `requests`, `approve` and `deny` (the approver's side of `ezc join`), and `rotate` (a new key in a new file, `freshKeyFile`, and `key_file` in `config.toml`). `ezc store rewrap` is in `storecmd.go`. |
| `cli/internal/cli/botcmd.go` | `ezc bot add`, `remove` and `rotate`: `giveBotKey` runs the change with the proof (`Backend.CanDecrypt` on every file) and the delivery (`ghcli.SecretSet`, the key on stdin) in `change.extra`, before the commit; `deleteBotSecrets` after a removal. The secret names `botSecret` (`EZC_AGE_KEY`) and `storeTokenSecret` (`EZC_STORE_TOKEN`). |
| `cli/internal/cli/joincmd.go` | `ezc join`: the clone, the key and the config as setup makes them, then a request (`recipients.Request`) pushed on its own branch `ezc/join-<name>` through `gitstore.PushBranch`, and the pull request. `ezc join --print` prints the `ezc user add` line instead. |
| `cli/internal/cli/repocmd.go`, `repos.go` | `ezc repo add`, `remove`, `list`, `check`, `uses` and `rewrap` (`repo init` is in `repo.go`): the store's `repos.yaml` changed and committed, never pushed, and `config.toml`'s `[checkouts]`; `check` and `uses` only read, `rewrap` writes a checkout's policy and encrypted files and runs no git there, and `repoTargets` says which repos a command acts on. `repos.go` holds the lookups: the working repo and its ID (`workingRepo`, `githubSlug`), a repo's checkout here (`checkoutOf`), the store's registry (`loadRepos`), and the re-wrap of a checkout (`rewrapRepo`, `repoGains`, `sayRewrap`). |
| `cli/internal/tui` | The terminal UI (Bubble Tea v2, Lip Gloss v2, Bubbles v2): the model, the four views, the confirm screen and the setup wizard. It imports no other ezc package and sees ezc only through the interfaces in `deps.go`; screens are golden files in `testdata/`. |
| `cli/internal/cli/tui.go` | `ezc tui` and the TUI's adapters: reads call what the commands call (`doctorReport`, `checkOne`, `load`, `openAccess`), and every change is a command line run in-process by `tuiCommands.Run`, without a terminal. |
| `cli/internal/migrate` | `ezc migrate`: the old tool's layout to `.ezc/`, built in a temporary folder and written only when the environment the old tool composes (`codegen shell`, parsed by `parseExports`) and the one ezc's resolver composes are identical. Recipients conversion, the `mise.toml` rewrite, and the scan for what still names the old tool. The one package that may name it; `cli/internal/cli/migratecmd.go` wires it to `System`. |
| `cli/internal/ghcli` | The `gh` command lines that are not setup's: `pr create` for a join request, `secret set` (the value on stdin only) and `secret delete`. An error carries one line of gh's stderr, each URL through `gitstore.ShowURL`, never stdin's content. |
| `cli/internal/setup` | What `ezc setup` does to a machine: creates the key file, creates the store as a git repo (manifest, `recipients.yaml`, policy, one commit) or clones it (`CloneShallowStore` for a CI job: with git and a token, one commit deep), adopts one made by hand (`Adopt`: a git repo, a manifest, and a registry and a policy where they are missing and the store holds no encrypted values yet), and publishes it to GitHub through `gh`. Flags, prompts and printing are in `cli/internal/cli/setupcmd.go`. It leaves alone whatever is already there. |
| `cli/internal/doctor` | Reports the health of the machine, the store and the repo (`ezc doctor`): checks, warnings and problems with their fixes, and the files in a `.ezc/` that ezc does not read. Never a value. |
| `cli/cmd/ezc` | `main.go` wires the process into `cli.Run` and holds the version. Its tests drive the built binary: `store_test.go` (setup, two machines, sync, `setup --ci`) and `access_test.go` (join and approve, remove, bots, rotate, and what an access change that crossed a write or was not pushed leaves) with real git and real sops, and a fake `gh` that only records. |
| `cli/share` | Files ezc writes elsewhere, embedded: the `env.sh` shim (`EnvSh`, `ShimVersion`) and the agent skills (`Skills`: `skills/ezc-convert`, `skills/ezc-migrate`), which `ezc setup` installs. |
| `bin/ezc` | Shim that builds `cli/bin/ezc` when a Go source changes and runs it; `direnv allow` puts `bin/` on PATH. |
| `README.md`, `docs/*.md` | User docs. The README is the homepage (what ezc is, quick start, a short command table); `docs/` holds the detail: `setup.md`, `store.md`, `access.md`, `repos.md`, `ci.md`, `tui.md`, `reference.md` (every command and flag, files, encryption, resolution) and `troubleshooting.md`. A command, flag or message that changes is changed there in the same commit. |
| `assets/readme/` | The README's SVGs (hero, layering diagram), written by hand: light background `#f8fafc`, text `#0f172a`, accent `#e85d26`, corners 4px at most, system fonts only. Render with `rsvg-convert -w 900` to check one. |
| `docs/superpowers/` | Design specs and implementation plans. Historical: never rewrite them to match the code. |
| `LICENSE` | MIT. |

`ezc`'s data is outside this repo, per user, in `EZC_HOME` (default `~/Library/ezc` on macOS and `~/.local/share/ezc` on Linux; `$XDG_DATA_HOME/ezc` applies on every OS when set). `ezc setup` writes `config.toml` there and creates or clones the global store, a git repo at `$EZC_HOME/store` whose values are in its `.ezc/`; `state.json` beside them records when the store's remote was last reached. `EZC_STORE` names another folder as the store, which `ezc setup` does not manage.

In a repo, `.ezc/` holds:

| Path | What it is |
| --- | --- |
| `.ezc/manifest.yaml` | What the repo needs from its environment. |
| `.ezc/common.yaml` | Plaintext values for every environment. |
| `.ezc/env.<name>.yaml` | Plaintext values for one environment; `env.local.yaml` is the default. |
| `.ezc/common.enc.yaml`, `.ezc/env.<name>.enc.yaml` | Encrypted values, for every environment and for one. |
| `.ezc/.sops.yaml` | The encryption policy, without which nothing can be encrypted in the folder. In the store `ezc setup` writes it from `recipients.yaml`; in a repo `ezc repo rewrap` writes it from the store's `recipients.yaml`, and leaves it for the repo's owner to commit. |
| `.ezc/env.sh` | The shim mise or direnv sources, written by `ezc repo init` from `cli/share/env.sh`. |

The store's `.ezc/` holds the same files without `env.sh`, and `recipients.yaml` (who can decrypt the store, by name and public key), `rotation-due.yaml` (the secrets a removed key could read, until each gets a new value; absent when there are none) and `requests/<name>.yaml` (a join request whose pull request was merged; a request normally stays on its branch `ezc/join-<name>`).

## Conventions

- **Commands reach the outside world only through `System`.** Packages under `cli/internal/` other than `cli` never call `os.Getenv`, `os.UserHomeDir` or `os.Exit`.
- **A malformed command line returns a `*UsageError` and exits 2**; any other failure exits 1. Use `noArgs`, `exactArgs`, `minArgs`, `maxArgs` and `verbs` from `cli.go`, never Cobra's own argument checks.
- **No command prints a value** except `ezc env export`, `ezc run` (to the command), `ezc get` and `ezc bot add|rotate --print-private`, which prints the bot's private key on stdout and nothing else there. Error messages and `--verbose` output carry names and paths only: a check's reason never includes the value that failed it, and a YAML parser's error text, which can quote the file, is never passed on (`invalidYAML` in `cli/internal/resolve/file.go`).
- **Only `backend/sops` names sops.** No other package contains `sops`, `.sops.yaml`, `SOPS_` or `ENC[`, apart from tests and `cli/internal/cli/scope.go`, which builds the default backend. Text about the tool or the key comes from the backend's own messages.
- **No value in output.** That covers stdout, stderr, error text, commit messages and anything passed through from a tool: the sops backend never passes sops's output on, and a commit message holds names and file names only.
- **Only `cli/internal/migrate` and the `ezc-migrate` skill name the tool ezc replaces.** Everywhere else under `cli/`, `grep -rniE 'fsconfig|fs-config|fs_config|four signals|\bipm\b' cli/ | grep -v -e '^cli/internal/migrate/' -e '^cli/share/skills/ezc-migrate/'` prints nothing; code elsewhere uses `migrate.OldTool` and `migrate.OldDir`.
- **Only `gitstore` builds `git` command lines.** Every other package calls its methods; `gh` and `brew` command lines are built in `setup`, and `gh`'s others in `ghcli`. Git, `gh`, `brew` and `sops` run only through `proc.Runner`.
- **A machine's private key is never printed** and is written to one place, the key file (`0600`, in a folder created `0700`). A bot's private key is never written to disk: it goes to `gh secret set` on stdin and, only with `--print-private`, to stdout. Nothing overwrites a key file, a store or a `config.toml` that is there.
- **A variable name matches `manifest.NamePattern`** (`^[A-Za-z_][A-Za-z0-9_]*$`), tested with `manifest.ValidName`: one rule for the manifest, the values files and the JSON Schema.
- **A values file is one flat mapping of `NAME: value`.** The resolver rejects what would silently change or drop a value: an anchor, an alias, a tag, a key defined twice, a second YAML document, a NUL byte.
- **`ezc env export` has two formats**, `shell` and `json`.
- **No defaults for values, anywhere.**
- **All CLI commands are Go**, built with [Cobra](https://cobra.dev), in `cli/internal/cli`. Flags are POSIX style: long flags take two dashes.
- **Tests set `EZC_HOME` to an absolute temporary path and `HOME` to a temporary directory** through the fake `System`; no test reads the real home, the real environment, a real key or the user's git config, and none uses the network. Git in tests runs with `GIT_CONFIG_GLOBAL` naming an empty temporary file and `GIT_CONFIG_NOSYSTEM=1` (`gitstore/gittest`); a remote is a bare repo in a temporary folder; keys are generated in the test; `gh` and `brew` are always faked.
- **Prose in Markdown is not hard-wrapped**: one line per paragraph or list item.
- **Comments are short**: one or two lines saying what a thing is.
- **Commit messages are conventional** (`feat(resolve): …`, `docs: …`).
